## 2. Google Console — uygulanacak adımlar

> Bu adımları **operatör** yapar; Console erişimi bende yok.

1. https://console.cloud.google.com/apis/credentials → projeyi seç.
2. OAuth 2.0 Client IDs listesinde `662374503405-m…` ile başlayan **Web application**
   istemcisini aç.
3. **Authorized redirect URIs** bölümünde **ADD URI**:
   ```
   https://api.130.162.247.20.sslip.io/api/v1/admin/escrow/step-up/callback
   ```
4. **Mevcut URI'yi SİLME.** `.../api/v1/auth/google/callback` yerinde kalmalı;
   silinirse mevcut giriş kırılır ve panelden önce tüm ürün etkilenir.
5. **SAVE.** Google değişikliği genelde saniyeler içinde uygular; bazı hesaplarda
   birkaç dakika gecikebilir.
6. Doğrulama (istemci secret'ı gerektirmez, tarayıcıda):
   ```
   https://accounts.google.com/o/oauth2/v2/auth?client_id=<CLIENT_ID>&redirect_uri=https%3A%2F%2Fapi.130.162.247.20.sslip.io%2Fapi%2Fv1%2Fadmin%2Fescrow%2Fstep-up%2Fcallback&response_type=code&scope=openid%20email%20profile&prompt=login&state=test
   ```
   - **Beklenen:** Google giriş/onay ekranı açılır (veya `redirect_uri_mismatch`
     **değil** bir hata).
   - **`Error 400: redirect_uri_mismatch`** görürsen URI kaydedilmemiştir veya
     birebir aynı değildir (şema/host/sondaki `/` dahil).
   - Bu testte `code` gelirse sayfa `.../step-up/callback?code=...` adresine düşer
     ve `403`/`stepup=denied` döner — **bu normaldir**, uygulama deploy edilmediği
     için uç nokta henüz yok. Önemli olan Google'ın URI'yi kabul etmesidir.
7. Console → **OAuth consent screen** → "Publishing status" **In production** olmalı.
   "Testing" modunda yalnızca ekli test kullanıcıları giriş yapabilir; step-up
   sırasında bu kişiler dışındakiler reddedilir.

### Neden `prompt=login` şart

`prompt=consent` ile Google, mevcut oturumu yeterli sayıp **şifre sormadan** geri
dönebilir. O durumda "yeniden kimlik doğrulama" yapılmamış olur. Kod bu yüzden
`prompt=login` gönderir (`google_provider.get_authorization_url(..., prompt="login")`).

## 3. Compose değişikliği (patch hazır, UYGULANMADI)

Dosya: `docs/patches/3.9.19b-escrow-readonly-mount.patch`

```yaml
      - /var/backups/tezlify-ram:/var/backups/tezlify-ram:ro
```

Uygulama (release penceresinde, onayla):

```bash
cd /opt/tezlify            # veya repo kökü
git apply --check docs/patches/3.9.19b-escrow-readonly-mount.patch   # önce kontrol
git apply         docs/patches/3.9.19b-escrow-readonly-mount.patch
```

### Doğrulanmış özellikler

| Kontrol | Sonuç |
|---|---|
| `git apply --check` | **OK** (repoya uygulanmadı) |
| Mount'u taşıyan servis | **yalnızca `backend`** (YAML ile doğrulandı) |
| Diğer servislerde değişiklik | **YOK** (gateway/caddy bayt-eşit) |
| `backend` volume listesinden çıkan | **YOK** (yalnızca 1 ekleme) |
| Mod | `ro` |
| Bağlanan | **dizin** (`/var/backups/tezlify-ram`), tek dosya değil |
| Top-level compose anahtarları | değişmedi |

**Neden dizin, tek dosya değil:** tek dosya bağlamak inode'a sabitlenir; escrow
yeniden yazıldığında (yeni inode) mount **eski** dosyayı göstermeye devam eder ve
panel sessizce bayat veri gösterir. Dizin bağlamak bu tuzağı önler.

## 4. İzinler: 0600 / 0700 korunuyor mu?

**Evet — ve bu tahmin değil, bu hostta ölçüldü.** Backend konteynerinde zaten
çalışan bir `:ro` bind mount var (`/opt/tezlify/monitoring`):

| Taraf | Mode | Owner |
|---|---|---|
| Host | `775` | `1001:1001` |
| Konteyner (aynı `:ro` mount) | `775` | `1001:1001` |

`findmnt` çıktısı: `ext4 ro,relatime,…` → `ro` gerçekten çerçeve seviyesinde.

Sonuçlar:
- Bind mount, inode'un **kendi mod bitlerini** taşır; `ro` yalnızca yazmayı engeller
  (`EROFS`), izinleri değiştirmez. Yani `0600` dosya / `0700` dizin **korunur**.
- Backend PID 1 **root** olduğu için `0600` dosya sahibi `1001` olsa da okunabilir.
  (Root olmayan bir kullanıcıya geçilirse panel `UNREACHABLE / permission_denied`
  döner — bu bilinçli bir fail-closed davranışıdır, sessiz boş veri değil.)
- `:ro` sayesinde uygulama bir hata yapsa bile escrow dosyasını **bozamaz**.

**Release sonrası yeniden doğrulama (zorunlu):**

```bash
docker exec tezlify-backend findmnt -T /var/backups/tezlify-ram -o TARGET,OPTIONS -n
# beklenen: /var/backups/tezlify-ram  ... ro,...

docker exec tezlify-backend stat -c '%n mode=%a owner=%u:%g' \
  /var/backups/tezlify-ram /var/backups/tezlify-ram/.key-escrow-v2
# beklenen: dizin 700, dosya 600, ikisi de 1001:1001

docker exec tezlify-backend sha256sum /var/backups/tezlify-ram/.key-escrow-v2
# beklenen: d03ed27ac2218f8b6f7e2e27000d401b8fea8566edec96e25b67f25e481365f4
```

## 5. Bayrak ve yetki: kapalı kalma kanıtı

`ESCROW_PANEL_ENABLED` için ölçülen matris (`Settings(_env_file=None, ...)`):

| Girdi | Sonuç |
|---|---|
| env yok | **False** |
| `''`, `' '`, `'0'`, `'false'`, `'no'`, `'off'`, `'n'`, `'f'` | **False** |
| `'y'`, `'t'`, `'yes'`, `'on'`, `'banana'` | **False** + uyarı (fail-closed) |
| `'1'`, `'true'`, `'TRUE'`, `' true '` | True |

`ESCROW_SUPER_ADMIN_EMAILS`: `''` ve `'   '` → `[]`; liste normalize edilip küçük
harfe çevriliyor (`' A@X.com , b@y.com '` → `['a@x.com','b@y.com']`).

Boş liste davranışı **testle** sabit: `require_super_admin` listeyi boş görünce
`403` döner (`test_empty_super_list_fails_closed`). Panel kapalıyken ise `404`
döner — kapalı bir özellik varlığını sızdırmaz (`test_panel_disabled_returns_404`).
