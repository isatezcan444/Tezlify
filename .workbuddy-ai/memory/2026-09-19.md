There is **no Alembic**; `migrations.py` *is* the migration layer and is driven from startup. The
"no startup runtime DDL" and "must be in the migration layer" constraints are therefore in tension as
literally written — resolved by keeping all DDL in `migrations.py` and none in any request/ingest path,
and stating that explicitly in the report.

### The race is real — measured
With the C-4 index removed, the barrier-synchronised N=6 parallel test persisted **five duplicate rows**
for one provider message. With the index present: exactly one row, one published id, `unread_count == 1`,
one loser rolling back via the pre-existing `except IntegrityError` in `ingest_gateway_event`
(`events.py:1380-1383`). **No production code change was needed** for "no unhandled IntegrityError" —
the constraint and that guard already compose. Dropping the losing delivery (rather than re-resolving to
the canonical row) is correct: re-broadcasting would be the duplicate event storm.

# 2026-09-19 (later still) — Phase 4 Addendum: class-wide G-3 sweep

## Why
The directive named one table (`lid_mappings`), but §6 asked for a reader matrix and §4 framed G-3 as a
tenant-isolation problem. So the sweep was extended to **every** `whatsapp_private.*` table and every gateway
read.

## THE DISCRIMINATOR (the reusable result — this is the generalisable rule)
An unscoped read is safe **only** when the key is **synthetic and globally unique**. It is a leak when the key
is a **natural key that legitimately repeats across tenants**.

| Key | Nature | Unscoped read |
|---|---|---|
| `processed_events.event_id` | `crypto.randomUUID()` per emission | **Safe** — global idempotency ledger is correct |
| `lid_mappings.lid_jid` | natural, repeats | **LEAK** |
| `history_sync_states.jid` | natural, repeats | **LEAK** |

Why the bug hides in review: for a synthetic key the pattern genuinely IS harmless, and it then gets copied
to a natural key.

## NEW FINDING — `history_sync_states` (latent, NOT live)
`history_evidence.py:86-92` had `else: ... WHERE jid = :jid ORDER BY updated_at DESC LIMIT 1` — a global read
on a natural key, leaking another tenant's `state` / `provider_checked` / `provider_msgs_returned`. It also
fed `has_more`, so it was a data-correctness issue too.
**Latent because all 3 callers guard** on a resolved session id (`whatsapp_service.py:739`, `:668`,
`sync.py:1642`) and `sync.py:1425` passes `str(gateway_id)`. Verified by reading each call site, not assumed.
**Fixed:** `session_id` is now required; with none it returns the fail-closed `NOT_CHECKED` default. Behaviour
unchanged for every existing caller — the duplicated guard became an enforced invariant.

## Everything else is BY DESIGN (with the reason)
- `processed_events` global dedup — synthetic UUID.
- admin ops aggregates (`whatsapp_admin_service.py:137,160,182`) — `require_admin` is an **ADMIN_EMAILS
  allow-list, fail-closed**; read-only ops centre; PII masked.
- `recovery.py:118` orphan scan — operator CLI (`scripts/recover_whatsapp_session.py`), its purpose IS orphan
  detection.
- gateway `listRestorableSessions` / outbox `claimPending` / `socket_leases` — **the gateway is shared
  infrastructure, not a tenant.** A global read inside it is not automatically a leak; the leak is using one
  tenant's data to serve a different tenant's session. Only the `DISTINCT ON` and the disk sweep crossed that
  line (both fixed).
- SAFE (already scoped): `sync.py:830`, `history_evidence.py:82`/`:298`, `relink.py:268`, `recovery.py:205`,
  `loadCredentials`, `getSignalKeys`.
