# Phase 3.8.2 — RAM snapshot feasibility (start `fef3569` → end `21a0688`, pushed)

**No deploy, no real export, no DB write, no gateway touch.** Only a diagnostics script + tests + doc.

## Export path already exists — no deploy needed
`GET /sessions/:sid/messages/bulk` returns the **stored record itself**, not a DTO
(`session-manager.js:1340` `all.push(m)`). Fields include `body`, `wa_message_id`, `conversation_id`,
`direction`, `message_type`, `status`, `created_at`, `sender_phone`, `media_id`, `quoted_message`, …
So full-payload export is possible **read-only today**; no new endpoint, no deploy.

## Measured on production (aggregates only, no payload written)
**99 chats / 9.133 records / 6,22 MB** (avg 714 B, max 53 KB). 0 duplicates, 0 missing-identity,
0 incomplete, 0 shortfall, 0 unstable chats. Chat ceiling 300 ⇒ **201 headroom**.
Both capped chats at exactly **2.000**: 38289 (person, 10-24→10-29), 38291 (**group**, 10-12→10-28);
0 id-less records in either.

## Two traps found (both would silently lose data)
1. **Naive offset pagination is unsafe.** `listAllMessages` re-sorts per request; a mid-pagination
   arrival shifts every offset. Falsified on 5 synthetic records: naive returned `A0,A1,A1,A2,A3`
   (**duplicate A1, missed NEW**); identity-set collection got all 5. Same class as 3.6b.
2. **Group jid trap.** A group's `contacts.phone_e164` holds `jid:<...>@g.us`. Digits-only
   normalisation turns it into a non-existent chat ⇒ my first probe reported **0 records** for 38291
   and it looked empty. Any tool that derives jids from the DB (not from the gateway) silently skips
   every group. `audit_memory_gap.py` handles it via the `jid:` branch.

## Media is NOT in RAM
`/app/media` 2,2 GB / 1.334 files with `.meta.json` sidecars; `raw-media-cache.json` persists 5.000
raw protos per session dir (8,0 MB active). Records carry `media_id` only ⇒ snapshot is a
**"RAM message-record backup"**, never call it a full backup.

## Built
`scripts/diagnostics/ram_snapshot.py` — identity-set pagination, `stable`/`shortfall` flags,
`sha256[:32]` identity tokens, content-free manifest (`records_sha256`, `identity_root_sha256`),
AES-256-GCM mirroring `encrypted-codec.js` (sha256(key)→32B, 12B nonce, AAD), refuses plaintext
without `--allow-plaintext`, refuses repo paths, restore only to scratch SQLite (refuses postgres
`DATABASE_URL`). `backend/tests/test_ram_snapshot.py` — **34 tests**, incl. structural pins that the
source contains no write SQL and `sqlite3.connect` appears only in `restore_to_sqlite`.
