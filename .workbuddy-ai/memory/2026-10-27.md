## WhatsApp chat list: "Henüz WhatsApp Mesajı Yok" on chats that are not empty (commit `acc468a`)

**Report.** User: some chats say "henüz whatsapp mesajı yok" even when the contact has a name, and the
chat list then looks mis-ordered.

**Measured, not assumed** (`docker exec tezlify-db psql` on prod, read-only):

| metric | value |
| --- | --- |
| conversations | 124 |
| `last_message_at IS NULL` | 0 |
| zero `messages` rows | **33** |
| messages but NULL timestamp | 0 |
| messages but NULL preview | 0 |
| zero rows + preview | 5 |
| all `messages` rows created in | one hour, 2026-10-26 21:00 (582 rows) |

The whole dataset came from a single re-pair at 21:24:04 (every conversation `created_at` identical).
The 33 chats carry a real `last_message_at` (from the gateway chat list) but no message objects, so
`message_count == 0` → `NO_MESSAGES` → "Henüz WhatsApp Mesajı Yok" on a row sitting at its true position
near the top. Ordering was never wrong; the *claim* was.

**Root cause.** `_list_conversations_impl` derived the state from `message_count` alone. `NO_MESSAGES`
is an assertion about the chat; zero local rows is an assertion about our copy.

**Not recoverable.** Probed the gateway directly (`docker exec tezlify-gateway node -e fetch(...)`):
chat list has the jid + timestamp, `messagesByChat` is empty, and even `fetch_provider=true` returns
`provider_status=NOT_REQUESTED` — the fast path in `session-manager.js` requires `isPagingOlder`
(`before`/`oldestMsgId`), and a chat with no rows has neither. `fetchMessageHistory` pages backwards
from an anchor, so `NO_ANCHOR` is the hard floor. Fix = truthfulness, not fabrication.

**Change.** New `last_message_state = "UNSYNCED"` (activity proof AND zero rows). Frontend: list row
falls back to `whatsapp.lastMessageUnsynced`, thread pane shows `whatsapp.historyUnavailable*` with a
retry, and rows from the session cache (no state field) key on `last_message_at` instead of defaulting
to "no messages". `NO_MESSAGES` now means no timestamp + no preview + no rows.

**Tests.** 799 passed across all `test_whatsapp*.py`; settings/stability/adversarial green. One pinned
expectation moved: `test_sync_conversations_forces_group_subjects_and_repairs` asserted `RESOLVED` for a
preview-without-rows group → now `UNSYNCED` (preview still lands, still asserted).

## Security: settings endpoints were anonymous (same commit, finding 1 of the review)

Verified live against production: `GET /api/v1/settings/smtp` → **200 without a token** (password field
was empty because SMTP is unconfigured — the leak was latent), `GET /settings/antiban` → 200.
`PATCH /settings/antiban` was equally open, i.e. anyone could zero every tenant's send delays.

Fix: `router = APIRouter(dependencies=[Depends(get_current_user)])` so new routes are closed by default;
`SmtpConfigResponse` no longer declares `password` (Pydantic drops it) and exposes `has_password`; the
service dict keeps the password for the internal send/test paths. UI sends auth already (`authFetch`),
so nothing broke; the password field is now blank with a "saved — leave empty to keep it" placeholder
and `save_smtp_config` retains the stored password on an empty value.

## Round 2 (`0626304`): pairing-token 404 + partial history gap

**Pairing 404.** `GET /pairing/{token}/qr` 404'd once the token was consumed, and the token is
consumed by whichever path wins — normally the event-driven promotion on `connection.open`, NOT the
browser poll. So the modal's 2.5 s fallback poll 404'd until it hit its failure threshold and reported
"bağlantı kurulamadı" for a line that had just connected (2×404 in 6 h, visible in the user's console).
Fix: bounded in-memory `_consumed_pairings` tombstone, tenant-scoped, written from BOTH consumers
(`get_pairing_qr` and `remove_ephemeral_pairing_by_gateway_id`). Cancel records nothing → still 404.
Restart drops it → degrades to today's behaviour. Pinned test changed: second poll now 200 CONNECTED
with the same session id (one row still asserted).

**Partial history gap.** `UNSYNCED` only covers zero rows. Chats with rows whose newest is far older
than the stamp stayed `RESOLVED` and silently ended early. Added `history_gap_seconds` (>600 s
threshold; reaction/call activity bumps the stamp without creating a row, and all 11 reaction chats
measured a 0 s gap). Live after deploy: exactly 2 flagged — 37791 (self chat, +20.4 h) and 37863
(+176.7 d); the 3.2-min case correctly excluded.

Tests: 839 passed (all WhatsApp + pairing/relink suites, random order), 6 new tombstone tests.
Deployed and verified: `.deployed-commit=0626304`, containers healthy, `/health` 200.

## Round 3: a preview is not a message (fabrication removed) + NOT NULL default drift

**First, a false alarm — recorded so nobody re-chases it.** I had flagged "conversations deleted while
272 message rows still reference ids < 37800" as data loss. **Falsified**: `min(messages.conversation_id)`
= `min(conversations.id)` = 37791, so **zero orphaned rows**; the 272 figure came from a bad measurement.
Counts did move (124→123 convs, 619→622→616 msgs) but **no delete path fired**: every boot migration
logged "verified", the only two code paths that clear a preview also NULL `last_message_at` (0 rows have
NULL), and 616 of 616 messages sit on existing conversations. Both remaining deletion sites
(`_ingest_conversation_deleted`, `_ingest_messages_deleted`) log at INFO and logged nothing.

**The real find: `get_messages` INVENTED a message from a preview string.** When the DB held 0 rows and
the conversation carried a preview, it INSERTed a `Message` (body = preview text) with
`wa_message_id = preview_<conv>_<epoch>`, and `ensure_conversation_preview_messages` did the same as SQL
at every boot. Live proof: one such row existed — conv 37833, `OUTBOUND/TEXT/READ`,
`body='Şu mesaja ❤️ ifadesini bıraktınız'` — a **reaction marker rendered as a message the user typed**.
Worse, `oldest_message_id` was then computed from that row and `sync.py` used it as `oldest_msg_id=`,
the **pagination anchor**: WhatsApp can never resolve `preview_…`, so the chat could never load history.
The "cure" for the false "no messages" claim guaranteed the disease it hid. Removed both writers;
`ensure_conversation_preview_messages` → `purge_synthetic_preview_messages` (deletes only
`^preview_[0-9]+_[0-9]+$`). `UNSYNCED` (§R) is the honest replacement. See invariants **S**.

**Second find, surfaced by the gate: `messages.is_view_once` was inserted as explicit NULL.**
`_insert_messages_resilient` builds raw VALUES dicts from `getattr(row, col, None)`, bypassing the ORM's
flush-time defaults, and patched only a hardcoded `("is_forwarded", "is_pinned")` list — so when
`is_view_once` was added, every synced insert broke on a NOT NULL schema (the pre-existing red
`test_insert_messages_resilient_heterogeneous_nulls`) while production silently stored NULLs because
`ALTER TABLE … ADD COLUMN is_view_once BOOLEAN DEFAULT FALSE` had made it **nullable** (prod: 616/616
non-NULL today only because that backfilled them; the NEXT synced message would be NULL). `_persist_sync_batch_safely`
carried a **second copy** of the same loop. Extracted `_normalize_message_insert_values` +
`_column_scalar_default` so the fallback is derived from the column (`nullable is False` + scalar
Python default) instead of a name list, and both writers share it.

**Falsified causation before fixing:** the `is_view_once` failure reproduces with my changes stashed
(`git stash` → same `IntegrityError`), so it is pre-existing, not mine.
