## Plan recorded for the next slice — SSRF-guarded link/media previews

Decisions taken while planning (do not re-litigate these without new evidence):

1. **Unfurling must never run on the chat-open path.** `get_messages` is `@profiled("chat_open")` and
   Phase 10.9 deliberately removed a per-message SELECT from it. An outbound HTTP fetch there would turn
   chat-open into seconds. So: cache hit = 1 batched query per page (mirror `reactions_by_message`), and a
   miss **schedules** the work (`asyncio.create_task`, the pattern already used in `sync.py`/`main.py`)
   and returns the message preview-less this round; the preview arrives on the next load or via WS.
2. **The cache is a table, not memory** (`link_previews`, keyed by normalized URL). Re-opening a 500-message
   thread must cost zero outbound requests. Mirrors the reactions decision.
3. **The SSRF guard is the whole risk.** It is the first place untrusted input causes outbound traffic.
   Block on the **resolved IP**, not the hostname, and re-validate every redirect hop — a check-then-fetch
   is the same TOCTOU shape as the `_ingest_message` race fixed in `f9e92fa`, and the loser here is an
   internal network read, not a dropped row.
4. **No new dependency**: `httpx>=0.27.0` and `beautifulsoup4>=0.12.0` are already in
   `backend/requirements.txt` and installed.
5. Preview **images** must be proxied through an authenticated route (model: `/media/{media_id}`), never
   hotlinked — hotlinking leaks the user's IP and breaks on referrer/CORS.
6. YouTube needs no scraping: `watch?v=ID` / `youtu.be/ID` → deterministic thumbnail + `youtube-nocookie`
   embed. Instagram blocks unauthenticated OG fetching, so plan an honest branded fallback card rather
   than a broken preview.

## Session 2 — the "machine is eating RAM" investigation, and the conversation-row menu

### What the user actually asked

"Bilgisayar aşırı şekilde rm/RAM kullanıyor sen çalıştırırken neden" — i.e. why does running my
verification commands consume the machine's memory. This turned out to be a real, measurable bug in
the gates, not an environment quirk. Answer: **`node:assert` + jsdom**.

### Root cause (measured, not theorised)

A jsdom gate was dying with `EXIT=137` and **completely empty stderr**, and the shell running it was
being killed too. Bisected with stderr markers to the exact statement: `assert.equal(found, null, ...)`
where `found` was a React-rendered `<iframe>`.

Node builds a failed assertion's message with `util.inspect(v, { depth: 1000, customInspect: false })`.
`customInspect: false` **disables jsdom's cheap custom inspect** and walks the element structurally,
React's `__reactFiber$*` / `__reactProps$*` back-references included:

| call | result |
| --- | --- |
| `inspect(iframe)` | 3,391 chars, RSS 186 MB unchanged |
| `inspect(iframe, { depth: 1000, customInspect: false })` | **137,861,117 chars** in 1.27 s, RSS 186 MB → **509 MB** |

So one failed assertion allocates ~137 MB of string plus the diff machinery. It is **native** memory,
not the JS heap — `--max-old-space-size=384` changed nothing and V8 never printed a heap-OOM. Hence
SIGKILL with no diagnostic.

**The fix that made the gate pass** was scoping the query to the container (`container.querySelector`
instead of `window.document.querySelector`), which was *also* a genuine false-positive bug: check 3's
portalled iframe stayed in `document.body`, so check 4's document-wide query found it. One change fixed
both a wrong assertion and the OOM.

### Fixed in this session

- `frontend/scripts/lib/safe-dom-assert.mjs` (new) — `hardenAssert()`. Deliberately **compare-first**:
  if neither side is a DOM node it delegates to the original; if one is and the comparison PASSES it
  stays silent (so legitimate `assert.equal(document.activeElement, input)` keeps working); only a
  FAILING element comparison throws a readable error instead of OOM-ing. Applied to all 9 jsdom gates.
- Element-valued assertions rewritten to boolean/attribute form in `verify-link-preview-dom.mjs`,
  `verify-message-reactions-dom.mjs` (4 sites), `verify-whatsapp-dom.mjs`.
- `verify-admin-ops-dom.mjs` — **passed all 13 checks and then hung forever** (no `process.exit()`;
  `pretendToBeVisual` rAF loop + React scheduler keep the loop alive). The runner SIGTERM'd it, so a
  green run read as `exit 137 / SIGTERM`. Added the explicit exit. This is the same trap already
  documented in `verify-link-preview-dom.mjs`.
- `frontend/scripts/verify-conversation-menu-dom.mjs` (new) — 9-check gate for the row menu.
- `npm run verify:link-preview`, `npm run verify:conv-menu` added to `frontend/package.json`.

### Real product bug found by the new gate

`ConversationList`'s list filter defines archived as `Boolean(c.is_archived) || c.status === 'ARCHIVED'`,
but the row's menu used only `status === 'ARCHIVED'`. So a chat archived **on the phone** appeared in the
Archived tab while its menu offered "Archive". Fixed with a primitive `isArchived?: boolean` row prop
(memo-safe) and one shared predicate. The gate's check 5 failed before the fix and passes after —
load-bearing.
