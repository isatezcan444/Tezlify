## Production frontend deploy — chat-thread singleton fix (`5916ff1`)

Shipped the fix for the stacking ChatThread bug (the one visible in the user's screenshot: several
chat panes stacked inside one hub Card, each contributing its own scroll area).

**Why it stacked (diagnosed 2026-09-25, from live console probes):**
The pane held N `ChatThread` fibers whose keys were the conversation ids the user had clicked
(`13795/13794/13796/13781`), under a single Card and a single 112-row sidebar, with **no error
thrown**. The deployed bundle had exactly one `ChatThread` call site (no `map`) and the source had no
imperative DOM movement, React production 18.3.1, `<font>` count 0 (so no translator/extension
mutation). Culprit: `key={selectedConv.id}` destroyed and rebuilt the whole thread subtree on every
conversation switch; when the teardown did not complete, the old root stayed in the pane and each
click appended another. One instance reported `msgCount: 0` while still rendering messages — direct
proof the fiber tree and the live DOM had desynchronised.

**Fix:** `ChatThread` gained a `conversationKey` prop. Identity change no longer destroys the
instance; it resets per-conversation state in the render phase (scroll/pin/guide state, near-bottom,
pill, prepend guards, K19 height cache/window/anchor/pin refs) and re-takes the opening position via
`convEpoch`. `hasContent` added to the initial-positioning effect deps — the gap where a message
arriving into an empty chat with no loading transition never took its opening position was
previously masked by the remount. `WhatsAppHubPage.tsx` uses `conversationKey={selectedConv.id}`
(the composer stays keyed for draft isolation); `LeadDetailDrawer.tsx` passes `conversationKey={lead.id}`.
A static contract in three verify files fails if `key=` returns.

**Deploy performed (approved by user):**

- Built off-box: `rm -rf dist && npm run build` → `index-3UEtgr4K.js` (879.16 kB), `index-5YKannVK.css`.
  No `frontend/package-lock.json` exists, so `npm ci` is structurally impossible — existing
  `node_modules` was reused.

  `rsync -az --delete`. sha256 matched local↔remote end-to-end.

  `docker compose -f docker-compose.prod.yml up -d --force-recreate --no-deps caddy`.
- Result: container sees `index-3UEtgr4K.js`; `curl https://localhost/ -H "Host: …"` → HTTP 200 and
  the served asset hashes to the same `670fe140…`. Caddy healthy. Backend/gateway `StartedAt`
  unchanged (2026-09-21T19:57) → `--no-deps` genuinely scoped, WhatsApp socket preserved.

**Verification:** build ✓ · verify:logic 43/43 ✓ · verify:dom 21/21 ✓ · verify:browser real Chrome
8/8 ✓ — including `H`: opening 6 conversations in a row leaves exactly one thread root in the pane.

**Separate pre-existing defect found (NOT caused by this deploy — static files only):**
`GET /api/v1/whatsapp/conversations/{id}/messages` returns **502** for conversations whose local row
count is below the page size. Chain: local rows < `page_size` -> on-demand provider hydration ->
gateway `?fetch_provider=true` returns **HTTP 200 but takes ~15,013-15,016 ms** -> backend's 15 s
ceiling trips -> `WhatsAppHistoryTimeout: Provider history chunk timed out for <jid>` -> endpoint maps
it to 502 (deliberately, "retryable state, not an empty conversation"). Observed on conversation
13907 (8 stored rows) and jids `6282245414751`, `905354931592`, `905413749073`; conversations with
>= 50 stored rows (13908/13909/13910) return 200 and never hit the gateway. So the timeout budget is
the mismatch, not the UI. UI behaviour is correct: skeletons while `loading`, then an
`EmptyState` + retry once `messageLoadState` flips to `error`.

**Trap re-hit:** used `grep "a\|b"` and got an empty result, briefly reading it as "no ChatThread in
the hub page". This is the documented BSD-grep BRE alternation trap — use `grep -E` or the Grep tool.

## PRODUCTION INCIDENT — WhatsApp line deleted, all conversations/messages lost (2026-09-25 23:17:04 UTC)

While investigating the 502, discovered that `conversations` (5067 ins / 5039 del) and `messages`
(45362 ins / 54576 del) were **empty**, with `max(id)` NULL. Cause, from the backend access log:

```
23:17:04  DELETE http://gateway:8787/sessions/eeacbbcf-88b1-4227-8687-ab760e445d71  -> 200
23:17:04  DELETE /api/v1/whatsapp/sessions/81  (from 104.28.244.150 = Cloudflare edge) -> 200
```

Deleting a line cascades to that line's conversations and messages (`Conversation.messages` is
`cascade="all, delete-orphan"`), and **all 111 conversations belonged to session 81**
(+905413749073) — so the whole WhatsApp dataset went with it. The gateway's session dir
`eeacbbcf-…` was also removed from the `tezlify_whatsapp_sessions` volume, so the line's Baileys
credentials are gone too.

**Who:** a browser client, not the probe. Verified my probe scripts contain no `delete`/`sessions`
calls (they only open the hub tab and click `button[data-conv-id]` rows). The log line immediately
preceding the DELETE is `GET /api/v1/whatsapp/sessions` — a screen the probe never opens. The delete
UI is a `Trash2` icon on `SessionCard.tsx` gated by `whatsapp.deleteSessionConfirm` ("…All synced
conversations and messages will be deleted as well. This action cannot be undone.").

**Damage / what survived:**
- Lost: all conversations + messages (no backup covers them), session 81 row, gateway auth state.
- Survived: `contacts` 1401, `lid_mappings` 10433, `event_outbox` 6605, `leads` 3,
  `whatsapp_sessions` 2 (old, SCAN_QR/RELINK_REQUIRED), media volume 73 MB / 29 files.

**Recovery is NOT possible from backups — proved, do not assume otherwise:**
- Sep 19 `predeploy_20260919_215146/db.dump` (4.6 MB): **schema-only** for `conversations`/`messages`
  (TABLE entries, no TABLE DATA entries). A non-trivial size does NOT imply usable content.
- Sep 16 `backups/postgres/*.dump` (31 MB): restored into a scratch DB — valid `PGDMP`, restores
  cleanly, but `conversations` = 0 and `messages` = 0 (those tables were empty on Sep 16).
- `archive_mode = off`, no replication slots → no PITR.
- Restoring a scratch DB requires `pg_restore -U tezlify`; without `-U` it tries OS user `root` and
  fails with `role "root" does not exist` (same trap as psql). Scratch DB was dropped after use.

**Consequence:** the WhatsApp line must be re-linked by scanning a QR code from the phone; the
message history cannot be restored. The 502 investigation is moot until the line is re-linked and
conversations re-sync.

**The fix** (3 files, uncommitted): `_hydrate_or_tolerate_provider_timeout` in `whatsapp_service.py`

`PROVIDER_UNAVAILABLE_COOLDOWN_S = 300` in `history_evidence.py`, plus `last_attempt_at` threaded

(a) timeout with `have_rows=True` → serve local rows instead of discarding them;
(b) recent TIMEOUT/PROVIDER_ERROR + local rows → skip the futile round-trip;

## End-to-end UI verification in production (real Chrome, 2026-09-26 02:53–02:58)

An API-level 200 is not enough for a complaint that was UI-level ("the pane doesn't work"), so the
chat pane was driven in real Chrome against `app.tezlify.com` with an ephemeral token.

**Verdict: the pane works. Every conversation tested rendered its messages.**
- Exactly **1** ChatThread fiber on every click (`PASS_single_thread`), so the singleton fix holds.
- **No 5xx and no error state** on any click; `consoleErrors` empty.
- conv 14007 (48 rows) → 48 bubbles in ~300 ms, stable.
- conv 14020 (15 rows) → 15 bubbles after ~15.2 s (provider timeout, then local rows — previously a 502).
- conv 14023 (15 rows) → **first** visit pays ~15 s; the **repeat** visit renders 15 bubbles in
  **308 ms** and holds for 22 s. The cooldown is visibly working in the UI, not just in the API.
- conv 14010 / 14022 (50 rows) → 50 bubbles in ~200 ms (>= page size, no provider call).

**Probe pitfall that cost three rewrites — record it:** classifying the pane by
`document.body.innerText.includes('No WhatsApp Messages')` is **unreliable**. That string stays in the
DOM *while messages are rendered*, so it produced false "EMPTY_STATE" verdicts on conversations whose
own screenshots showed 15–48 bubbles. It even flips True/False between consecutive samples on the same
conversation. Two more traps: polling right after `click()` catches the pre-load frame (skeletons +
`messages: []`) and reports a bogus 1 ms "empty"; and a single sample can disagree with a screenshot
taken 200 ms later.

What actually works — sample a **timeline** every 250 ms and trust counters that cannot be faked:
- fiber census `msgCount` (the `messages` array the component really received) — authoritative;
- DOM bubble count via `div[class*="max-w-[85%]"][class*="px-4"][class*="py-2.5"]` (ChatBubble's root);
- `div.overflow-y-auto.space-y-1` presence + its `innerText.length` (the scroller only exists when rows
  are rendered, so `-1` distinguishes "no scroller" from "scroller with no text").
Require the state to hold across consecutive samples before classifying, and remember that a 15-row
conversation legitimately sits in the loading state for ~15 s on a first visit — do not call that a
failure.

**Residual confirmed as low-impact:** the 19 zero-row conversations are all *stale* — newest
`last_message_at` 2026-08-27, oldest 2026-03-24, 4 with no timestamp at all — and none appear in the
top 8 by recency, which all hold 15–51 rows. So they are not in the user's active path.
