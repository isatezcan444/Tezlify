## Production frontend deploy — chat-thread singleton fix (`5916ff1`)

Shipped the fix for the stacking ChatThread bug (the one visible in the user's screenshot: several
chat panes stacked inside one hub Card, each contributing its own scroll area).

**Why it stacked (diagnosed 2026-09-25, from live console probes):**
The pane held N `ChatThread` fibers whose keys were the conversation ids the user had clicked
(`13795/13794/13796/13781`), under a single Card and a single 112-row sidebar, with **no error
thrown**. The deployed bundle had exactly one `ChatThread` call site (no `map`) and the source had no
imperative DOM movement, React production 18.3.1, `<font>` count 0 (so no translator/extension
mutation). Culprit: `key={selectedConv.id}` destroyed and rebuilt the whole thread subtree on every
conversation switch; when the teardown did not complete, the old root stayed in the pane and each
click appended another. One instance reported `msgCount: 0` while still rendering messages — direct
proof the fiber tree and the live DOM had desynchronised.

instance; it resets per-conversation state in the render phase (scroll/pin/guide state, near-bottom,

`convEpoch`. `hasContent` added to the initial-positioning effect deps — the gap where a message
arriving into an empty chat with no loading transition never took its opening position was
previously masked by the remount. `WhatsAppHubPage.tsx` uses `conversationKey={selectedConv.id}`
(the composer stays keyed for draft isolation); `LeadDetailDrawer.tsx` passes `conversationKey={lead.id}`.
A static contract in three verify files fails if `key=` returns.

**Verdict: the pane works. Every conversation tested rendered its messages.**

- **No 5xx and no error state** on any click; `consoleErrors` empty.
- conv 14007 (48 rows) → 48 bubbles in ~300 ms, stable.
- conv 14020 (15 rows) → 15 bubbles after ~15.2 s (provider timeout, then local rows — previously a 502).
- conv 14023 (15 rows) → **first** visit pays ~15 s; the **repeat** visit renders 15 bubbles in

- conv 14010 / 14022 (50 rows) → 50 bubbles in ~200 ms (>= page size, no provider call).

**Probe pitfall that cost three rewrites — record it:** classifying the pane by
`document.body.innerText.includes('No WhatsApp Messages')` is **unreliable**. That string stays in the
DOM *while messages are rendered*, so it produced false "EMPTY_STATE" verdicts on conversations whose
own screenshots showed 15–48 bubbles. It even flips True/False between consecutive samples on the same
conversation. Two more traps: polling right after `click()` catches the pre-load frame (skeletons +
`messages: []`) and reports a bogus 1 ms "empty"; and a single sample can disagree with a screenshot
taken 200 ms later.

What actually works — sample a **timeline** every 250 ms and trust counters that cannot be faked:
- fiber census `msgCount` (the `messages` array the component really received) — authoritative;
- DOM bubble count via `div[class*="max-w-[85%]"][class*="px-4"][class*="py-2.5"]` (ChatBubble's root);
- `div.overflow-y-auto.space-y-1` presence + its `innerText.length` (the scroller only exists when rows
  are rendered, so `-1` distinguishes "no scroller" from "scroller with no text").
Require the state to hold across consecutive samples before classifying, and remember that a 15-row
conversation legitimately sits in the loading state for ~15 s on a first visit — do not call that a
failure.

**Residual confirmed as low-impact:** the 19 zero-row conversations are all *stale* — newest
`last_message_at` 2026-08-27, oldest 2026-03-24, 4 with no timestamp at all — and none appear in the
top 8 by recency, which all hold 15–51 rows. So they are not in the user's active path.

## Remaining UX issue: the ~15 s first-open wait (diagnosed, NOT changed)

The one user-visible symptom left is latency, and it is the literal reading of the original complaint
("every time I click it tries to load new messages"). Opening a conversation with fewer than
`page_size` local rows blocks the **first paint** on a "fetch older messages" round-trip.

Exact chain, traced in source:
- `backend/app/services/whatsapp_service.py:761` — `len(rows) < page_size` → the `else` branch runs even
  when `before is None` (i.e. a plain open, not a pagination), so the open path calls the provider.
- `sync.py:1825` — `gateway_client.get_messages(..., fetch_provider=True)`.
- `whatsapp_gateway.py:222` — `get_messages()` sends only `limit/before/fetch_provider/oldest_msg_*`;
  it has **no** `timeout_ms` parameter.
- `whatsapp-gateway/src/index.js:389` — the `GET /messages` route reads exactly those query keys and
  **does not read `timeout_ms`**, so `session-manager.js:660`'s hardcoded `timeoutMs = 15000` always
  applies. (`POST /conversations/:jid/history` at `index.js:411` *does* honour `timeout_ms`, and the
  backend client's `request_older_history()` already exposes it — the GET path is the gap.)
- Result: gateway waits 15 s for the phone, returns 200 with `provider_status=TIMEOUT`, the backend's
  `_hydrate_or_tolerate_provider_timeout` serves local rows. So it is a **wait**, not an error.

Measured: provider answered 5× (fast, ~2.6 s, `HAS_MORE`, `timeout_count 0`) and timed out 5× (15 s) in
one hour — roughly a coin flip per conversation, decided by whether the phone answers the history PDO.
`WHATSAPP_GATEWAY_TIMEOUT` (30 s) is the httpx timeout to the gateway and is *not* the binding limit.

Why it was left alone: every fix needs a **gateway** change (the GET route must forward `timeout_ms`),
and the gateway runs `WHATSAPP_AUTO_RESTORE: "false"`, so restarting it does not re-attach the live
line. `POST /sessions/restore` (`index.js:240`) can re-attach from persisted creds without a QR, so a
restart is *recoverable* — but after the 2026-09-25 data-loss incident and a fresh re-link, that risk
was not taken unilaterally. Options: (a) gateway route forwards `timeout_ms` + backend sends a short
value (~4 s) for the open path, keeping 15 s for explicit pagination; (b) stop blocking first paint at
all and hydrate only on real pagination (`before is not None`) — backend-only, but it changes tested
hydration semantics; (c) leave as is — keep the phone online and hydration is usually fast.

## RESOLVED: the ~15 s first-open wait is now bounded to ~4 s (verified in production)

Option (a) was chosen by the user and shipped as `6c7214a`. The GET route in
`whatsapp-gateway/src/index.js:389` now reads `timeout_ms` and forwards
`timeoutMs: parseInt(timeout_ms, 10)`; `whatsapp_gateway.get_messages()` gained
`timeout_ms`; `sync._hydrate_messages_on_demand()` gained `provider_timeout_ms` and forwards it;
`whatsapp_service.get_messages()` passes `OPEN_PATH_PROVIDER_TIMEOUT_MS = 4000` **only when the
request's own `before` cursor is absent**, i.e. a plain open. An explicit "load older" keeps `None`
→ the gateway's 15000 default.

**Where the budget must be decided.** Not inside `_hydrate_or_tolerate_provider_timeout` /
`_hydrate_messages_on_demand`: in that branch `before_ts_ms` is *always* set (it is the oldest local
row's timestamp), on both the plain-open and the pagination path, so it cannot discriminate. Only the
call site knows whether the *request* carried a cursor. (This cost one failed test: `test_25` asserted
`None == 4000` until the decision moved out.)

**Deploy:** partial-file checkout of 4 files (`whatsapp_service.py`, `whatsapp_gateway.py`, `sync.py`,
`index.js`) + `docker compose up -d --no-deps backend` and `... --no-deps gateway`. Backend
`00:11:14`, gateway `00:12:16`; db and caddy untouched. Gateway restart does **not** re-attach the
line (`WHATSAPP_AUTO_RESTORE=false`), so `POST /sessions/restore` was required — it re-attached
without a QR: `{"status":"ok","discovered":1,"restored":1}`, session
`4b69b1c0-50d8-4fb7-a96d-4e032811f1a8` CONNECTED `+905413749073`.

**Measured, from the production host (the sandbox proxy 502s on `app.tezlify.com`; Caddy is local
there, so the probe runs over ssh):**

|---|---|---|---|
| plain open, 15 rows | 14021 / 14032 / 14059 / 14026 | TIMEOUT | **4189.7 / 4047.0 / 4051.7 / 4045.2 ms** |
| plain open, repeat ≤300 s | same | cooldown skip | 21–57 ms |

**Pagination still 502s on a provider timeout — deliberately.** With a cursor the base query returns

pre-existing and unchanged by the budget work (it also used 15000 before).

**Do not trust `document.body.innerText.includes('No WhatsApp Messages')`.** In the loading state the
string is already present, so it reads `true` while the pane is *about to* render 15 messages. The
fiber `msgCount` and the structural DOM count are the ground truth; the screenshots agree with them,
the innerText check does not.

**Sandbox notes:** the local sandbox has `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:59508`, which
tunnels `app.tezlify.com` into a 502 — use the production host for API probes. Playwright lives only
in the repo `venv` (`venv/bin/python`), not in the managed Python. Production is **PostgreSQL**, not
SQLite: the `tezlify.db` at the repo/host root is stale, `sqlite3` is not installed on the host, and
`history_sync_states` is keyed `(session_id, jid)` — so joining on `jid` alone duplicates rows across
sessions and inflates `count(m.id)`. Always aggregate messages in a separate subquery.
