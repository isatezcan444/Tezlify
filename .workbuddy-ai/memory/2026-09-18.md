### Root causes confirmed (not hypotheses)

- **H-1 (P1) — history evidence session id type mismatch.** `whatsapp_private.history_sync_states.session_id`
  is TEXT holding the **gateway UUID** (written as `str(session_row.gateway_id)`), but the facade read it
  with `str(conv.session_id)` (integer PK). Result: `is_history_exhausted_or_stalled()` was always False
  (provider re-requested on every scroll) and `get_history_evidence()` always returned defaults →
  `has_more` permanently True. The correct helper `_conversation_gateway_id` was already imported and unused.
- **I-1 (P1) — push name leaked into `contact.display_name`.** `_upsert_contact`'s create branch was the one
  writer the `f6ec68d` fix missed; `safe_display_name` never consulted `name_source`, so WS `name` leaked the
  push name while REST was protected (REST/WS divergence). `_set_contact_name` could not clear it either
  (`current_rank > NAME_RANK["push"]` → `2 > 2` → False).
- **I-3 (P1) — REST/WS payload field divergence.** `conversations_updated` emitted `lead_phone` while the
  frontend mapper read `phone`; the merge `{...existing, ...mapped}` spread explicit `undefined` over known
  state, wiping name and phone → "Kişi"/"Contact" fallback. Fixed on both sides.
- **S-1 (P1) — wrong broadcast kwarg.** `ws_manager.broadcast(..., tenant_id=...)`; real param is
  `target_user_id`. `TypeError` swallowed at `logger.debug` → relink state never reached the UI.
- **G-1 (P1) — gateway truthfulness violation.** `markConversationRead` zeroed `unread_count` and emitted
  `conversation_read: 0` even when the provider call failed, contradicting its own code comment.
- **C-1 (P1) — `UnboundLocalError`** in `_upsert_contact` self-identity branch silently dropped events.
- **G-2 (P1) — `pino` logger referenced but never imported** in gateway `src/index.js` → ReferenceError.
- **F-1..F-4 (P2/P1)** — fake-success archive/close with no backend route; `search` param never sent though
  the backend supported it; silent refresh discarding paged-in rows; stale-response race showing wrong chat.

### Phase 2 — second pass: §31 consolidation finished (+ new G-8 bug)

Finishing §31 (the canonical identity helper was only partly adopted) surfaced a real bug.

**NEW BUG — the frontend defeated the gateway's G-8 fix.**
`WhatsAppQrConnectModal` pre-normalized the pairing phone in the browser
(`replace(/\D/g,'')` + `00` strip + `^5\d{9}$` → `90…`) and sent the *normalized* digits.
The gateway's G-8 guard is `isInternational = raw.startsWith('+') || raw.startsWith('00')`,
so it could NEVER fire for anything typed in that modal:
- `+1 512 345 6789` → silently `905123456789`
- `005512345678` (Brazil) → silently `905512345678`
Fix: modal sends the RAW input; the gateway is the single normalization authority.

**§31 consolidation now complete — the `jid:`/phone regex exists in EXACTLY ONE module:**
- `whatsappOrdering.getConversationIdentityKey` → delegates to `extractCleanPhone`
- `WhatsAppHubPage` `contact_synced` avatar match → `extractCleanPhone` + new `stripJidPrefix`
- `whatsappPreview.isRawIdentityName` → delegates to `isRawWhatsAppJid`
- new canonical export `stripJidPrefix(value)`

Behaviour improvements (both safe direction): a LID is no longer keyed as a phone
(`123…@lid` used to become `phone:+123…`), and equivalent spellings of one number now
collapse onto one identity key (`+905321234567` / `05321234567` / `5321234567`).
Verified: `replace(/^jid:/` and `replace(/\D/g` appear ONLY in `whatsappIdentity.ts`
across all of `frontend/src`; `slice(-10)` is gone.

### Phase 2 — third pass: truthfulness hardening (§1.1)

I had marked the audit's `status or "SENT"` finding FIXED **without verifying it**. Traced it

→ the `or "SENT"` branch is unreachable. Corrected the audit matrix label to `HARDENED` + trace.

**Hardened anyway** (a `"SENT"` default is exactly what AGENTS.md §1.1 forbids, and would become

Tests added: 3 backend (raising send → 502 not 200; schema status required; no `or "SENT"` in
